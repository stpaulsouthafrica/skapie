# First bounded check on macOS

Phase 11.4.1–5 uses one trusted preset: an installed Git binary with argv `diff --check`. Check Spec selects it, Run Check starts it after a separate Write Scope is connected, and Check Result shows its category and before/after Git status. The model has no command runner tool. Cables do not start a process.

## Signed sandbox probe

On 25 September 2026, a locally built, release-signed sandboxed Skapie app was run with a temporary probe entrypoint. Its embedded sandbox entitlement stayed enabled. `Process.run('/usr/bin/git', ['--version'])` returned `xcrun: error: cannot be used within an App Sandbox.` Direct installed Git at `/Library/Developer/CommandLineTools/usr/bin/git` and `/Applications/Xcode.app/Contents/Developer/usr/bin/git` both returned exit 0 for `--version`. After restoring a separately chosen Write Scope, a child process started successfully in that folder. The native fixed-command runner then returned `exit_0`, exit code 0, known before/after Git status, and `stopUncertain=false` for `diff --check` in a disposable Git setup. Temporary Git metadata was moved out of the selected folder after the probe. The normal release app was rebuilt afterwards.

This proves the direct path for this installed binary and selected folder on this Mac. It does not prove arbitrary executables are permitted. The app does not add the user-selected executable entitlement, use a helper, or disable App Sandbox. An executable inside a Repository read-only grant is never offered as a command; the check runner requires the separate Write Scope both in Dart and at the native channel boundary. Apple's [App Sandbox file access guidance](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox) distinguishes user-selected file access from executable access.

## Authority and bounds

- The preset has no shell and no editable executable or argv fields. The native host resolves direct Git from Command Line Tools or Xcode; if neither is installed, the check reports an infrastructure error. `/usr/bin/git` is not used.
- Git runs with cwd set to the selected write folder, `PATH=/usr/bin:/bin`, C locale, no inherited environment, no Git system/global config, disabled optional locks, and terminal prompts disabled. Git status is sampled before and after the check. Git status is a snapshot, not a complete filesystem diff; it can miss edits to ignored files or content changes in an already untracked file.
- The check has a 30-second limit; Git status snapshots each have an 8-second limit. Each output stream is drained with a byte cap. Native `posix_spawn` starts a new process group, and Cancel/timeout signals the group, then escalates to SIGKILL. An escaped descendant or uncertain stop is reported rather than called a success.
- The app's `network.client` entitlement remains enabled, so the UI says network is allowed. This fixed Git command has no network operation. The working directory is not filesystem or network isolation; the child may retain other authority the app already holds.
- The Result kit stores a short outcome and redacted Git status snapshots. It sends only the short summary to LLM Context on a later user-started turn. The Check Result Inspector shows the latest redacted output while chunks arrive and opens the board's run ledger, with redacted output chunks and each check's actual argv, cwd, environment key names, times, exit code, truncation/cancellation flags, and Git state. The ledger file sits beside the board scene as `scene.json.runs.json`.
- Output is held until a complete line can be redacted; a line longer than 4096 characters is withheld. Common credential assignments, bearer tokens, API key prefixes, and JWT-shaped values are masked before display or saving. This is pattern-based redaction, so do not use a check that may deliberately print real credentials.
- The five outcome categories are exit 0, nonzero exit, timeout, cancelled, and infrastructure error. Exit 0 means only this command exited 0. It does not mean the project tests passed or the agent's broader task is complete. Test-specific parsers and the separate Repeat Check action remain later work.

To try it, use a disposable Git repository. Choose that folder in Write Scope, place and cable Check Spec → Run Check → Check Result, and cable Write Scope → Run Check Write. Select the Git preset in Check Spec. Nothing runs until you confirm Run in the Run Check Inspector. Open **Check Result → Open check run ledger** to inspect the redacted evidence. For a visible nonzero exit, add trailing whitespace to a tracked file and leave that change unstaged. For a redaction probe, use a tracked filename containing a fake value such as `sk-test-secret-1234567890.txt`; the Git status and diagnostic paths should mask it in both the inspector and saved ledger. Many trailing-whitespace lines can exercise the output cap and its Truncated label. Restore the disposable repository when done.
